# Packaging

Release packages of the app. They never contain game data: the player imports it from
their own disc in the setup wizard. Outputs go to the gitignored `dist/`; nothing here
uploads or installs anything.

## Guard and stage manifest

`packaging/macos/stage.txt` lists every file that may be in the macOS app, with its
source in the repository (or `@name` for files the build makes: binary, Info.plist,
icon, code signature). `packaging/guard.py` (Python 3, standard library only):

- `stage` copies the listed repository files into the app. Files from
  `tools/upscalers/` (runner, model, licences) are copied only when their SHA-256 matches
  `tools/upscalers/upscaler.lock.json`.
- `check` walks the built app and fails on: game data and the original's files
  (`.smk .dat .wav .iso .sav .upk`, `Milionar.exe`, `Smackw32.dll`, `game.ico`), symlinks,
  special files, hardlinks, extended attributes other than `com.apple.provenance` (set by
  the system, cannot be removed), files or directories not in the manifest, missing
  entries, pinned files whose hash changed, and files containing strings of the build
  machine or its user. Those strings are read at run time and never written to the
  repository: home, checkout, `CARGO_HOME` and `RUSTUP_HOME`, the login name, the global
  git `user.name` and `user.email` (unless equal to this repository's own identity), the
  comma-separated `MILIONAR_GUARD_FORBID` and the lines of the gitignored
  `packaging/.guard-forbid.local`. `MILIONAR_GUARD_ALLOW` (comma-separated plain words;
  entries with `/`, `\`, `@` or whitespace are ignored) drops a login name that is a
  common word: the release workflow sets it to `runner`, the GitHub macOS runner's user,
  which our own notices contain. It never drops home or checkout paths, the git identity
  or an entry of `MILIONAR_GUARD_FORBID` / `.guard-forbid.local`. A pinned file whose
  SHA-256 matches its pin in `tools/upscalers/upscaler.lock.json` is not searched for
  these strings: its bytes are upstream's (the macOS runner was built on a GitHub runner
  and carries that runner's home path, the same as our CI's). All other checks still
  apply to it.
- `hashes` writes a `sha256sum`-style list of a tree.

Tests: `python3 -m unittest discover -s packaging`

## Licences shipped with both packages

`packaging/licenses/` holds two files that both stage manifests list:

- `SDL3-zlib.txt`: SDL 3.4.20's `LICENSE.txt` (zlib) and the notices of the parts SDL
  builds in (HIDAPI under its BSD-style licence, yuv2rgb BSD-3-Clause, the SunPro notice of
  SDL's libm), copied unchanged
  from the `sdl3-src` 3.4.20 crate; the header names each source file and its SHA-256.
- `rust-crates.html`: every crates.io crate built into `milionar` for the two shipped
  targets, with its licence text. Generated by the pinned cargo-about from `about.toml` and
  `about.hbs` with `tools/release/gen-licenses.sh`; `--check` fails when it no longer
  matches `Cargo.lock` (run in the release workflow). Regenerate and commit it whenever
  `Cargo.lock` changes. Pin and install command: `docs/build.md`.

## macOS (arm64)

    packaging/macos/build-app.sh      # dist/Milionar.app
    packaging/macos/build-dmg.sh      # dist/Milionar-<version>-macos-arm64.dmg (+ .sha256 files)
    packaging/macos/check-launch.sh SHOT_DIR [EMPTY_DATA_DIR]

Needs the toolchain from `rust-toolchain.toml`, CMake, Python 3 and the Xcode command line
tools. The runner and model come from `tools/upscalers/realesrgan-20220424/`
(`tools/fetch-upscaler.sh macos` is run when they are missing).

`build-app.sh`:

1. builds `milionar` for `aarch64-apple-darwin` into `target/package/` with
   `MACOSX_DEPLOYMENT_TARGET=11.0` and path remapping (no home or checkout paths in the
   binary); extra arguments go to cargo (`--features test-hooks`);
2. checks the binary is arm64 and links only system libraries (SDL is static);
3. reads the minimum macOS of the binary and the runner (`vtool -show-build`) and writes
   the higher one into `LSMinimumSystemVersion`;
4. stages the manifest files, renders `Info.plist` from `Info.plist.in` (version from
   `apps/milionar/Cargo.toml`), draws the icon with `packaging/icon/make-icon.py` and packs
   it with `sips` and `iconutil`;
5. runs the guard, signs ad hoc, runs `codesign --verify --deep --strict` and the guard
   again.

Bundle layout (`Contents/`): `MacOS/milionar`, `Info.plist`, `Resources/milionar.icns`,
`Resources/upscaler/realesrgan-ncnn-vulkan` and `Resources/upscaler/models/realesr-animevideov3-x3.{param,bin}`
(where the app looks for the runner), `Resources/fonts/LiberationSans-Regular.ttf` (also
embedded in the binary; shipped beside its licence), `Resources/LICENSE`,
`Resources/THIRD_PARTY_NOTICES.md` and `Resources/licenses/` (runner components and the
font's OFL, `SDL3-zlib.txt` and `rust-crates.html`, both from `packaging/licenses/`, see
below).

Signing: ad hoc only (`codesign -s -`), no Developer ID and no notarisation. The runner is
the upstream universal file, unchanged: it already carries an ad hoc linker signature on
its arm64 slice, and re-signing would change its bytes and break the SHA-256 pin the app
checks before running it. Its arm64 signature is verified, then the app is signed, which
seals the runner and models as resources.

`build-dmg.sh` checks the app again, copies it (without xattrs or resource forks) and
guards the copy, adds an `Applications` symlink (outside the guarded app tree), makes a
compressed UDZO image and verifies it. It then mounts the image read-only, checks that it
holds only the app and the symlink, guards and verifies the mounted app, and writes
`<dmg>.sha256` and `Milionar-<version>-macos-arm64.app.sha256` (every file of the app in
the image).

`check-launch.sh` starts the release `dist/Milionar.app` with an empty data dir, through
`open -n` and then directly: it must stay up, log the setup wizard and exit with status 0
on SIGTERM. Then it builds a `test-hooks` variant into `dist/check/`, runs it with the
normal video driver, captures the window and checks the wizard again (log lines, no
`game/` dir, a capture written).

`build-app.sh` clears extended attributes (`xattr -cr`) on the staged app before signing.

### Opening an ad hoc signed app

The app is not notarised, so Gatekeeper blocks it when it comes from a download. Copy it to
Applications, then Control-click it and choose Open (or allow it under System Settings,
Privacy and Security). Alternatively: `xattr -dr com.apple.quarantine /Applications/Milionar.app`.

## Windows (x64)

    packaging/windows/build-tree.sh       # dist/Milionar-windows-x64/ (+ <version>-windows-x64.tree.sha256)
    packaging/windows/build-installer.sh  # dist/Milionar-<version>-windows-x64-setup.exe (+ .sha256)

`build-tree.sh` cross-builds on macOS with llvm-mingw (`tools/build-windows.sh`, target
`x86_64-pc-windows-gnullvm`, see `docs/build.md`; the rustup toolchain is put first in
`PATH`). It:

1. draws `target/package/milionar.ico` with `packaging/icon/make-icon.py` (BGRA bitmaps
   16-64 px and a PNG entry at 256 px) and builds `milionar.exe` into `target/package/` with
   `MILIONAR_WINDOWS_ICON` set and the same path remapping as macOS (`--remap-path-prefix`
   for Rust, `-ffile-prefix-map` in `CFLAGS_x86_64_pc_windows_gnullvm` for SDL's CMake
   build);
2. checks the exe: x86-64, GUI subsystem, imports only DLLs of Windows itself (SDL,
   libunwind and the mingw-w64 runtime are static; the UCRT is part of Windows 10+), has
   the manifest, version and icon resources; checks that the runner imports only
   `vcomp140.dll`, `vulkan-1.dll` and system DLLs;
3. stages `packaging/windows/stage.txt`, copies the exe and runs the guard, then writes
   the SHA-256 list of the tree.

Resources of `milionar.exe` (all in `packaging/windows/`, compiled by `apps/milionar/build.rs`
with llvm-mingw's windres): `app.rc` embeds `app.manifest` and includes the version
resource rendered from `version.rc.in` (version from `apps/milionar/Cargo.toml`, company
`007hacky007`); the icon is added when `MILIONAR_WINDOWS_ICON` names an `.ico`. Plain
`tools/build-windows.sh` builds get manifest and version but no icon. MSVC builds embed
only the manifest (through the linker).

Tree layout (installed unchanged into the install folder): `milionar.exe`,
`upscaler/realesrgan-ncnn-vulkan.exe`, `upscaler/vcomp140.dll` and
`upscaler/models/realesr-animevideov3-x3.{param,bin}` (where the app looks for the runner,
all pinned in `tools/upscalers/upscaler.lock.json`; never `vcomp140d.dll`, the demo media or
other models), `fonts/LiberationSans-Regular.ttf`, `LICENSE`, `THIRD_PARTY_NOTICES.md` and
`licenses/` (runner components, the font's OFL, the LLVM and mingw-w64 runtime notices of
the llvm-mingw pieces linked into `milionar.exe`, the terms of `vcomp140.dll`, and the
SDL and Rust crate licences as for macOS).

The guard forbids the name `Milionar.exe` of the original game in any case. Only one
exception: our own exe, at exactly `milionar.exe` (tree root, lower case), listed as
`@binary` in the manifest, and in the built tree a PE image for x86-64 (machine 0x8664;
the original is a 32-bit i386 PE). Any other spelling or place, or an i386 or non-PE file
there, fails.

`build-installer.sh` checks the tree with the guard again and compiles
`packaging/windows/milionar.iss` with Inno Setup 6, then scans the installer for the
build machine's strings and writes `<setup>.sha256`. ISCC comes from:

- `ISCC=<path to ISCC.exe>`: run directly (Windows CI under Git Bash; paths go through
  `cygpath -w` when available, and `MSYS_NO_PATHCONV=1` / `MSYS2_ARG_CONV_EXCL='*'` stop
  MSYS from rewriting the `/Qp /D /O /F` switches as paths). The host needs Python 3.11+
  (`tomllib`) as `python3`; the guard runs on Windows too (no `pwd`, no xattr check there;
  its needles add `USERNAME`, `USERPROFILE` and `HOME`, in `\` and `/` spelling);
- otherwise wine (`WINE`, default `wine`): Inno Setup as pinned in
  `tools/upscalers/innosetup.lock.json` (URL, SHA-256, size) is downloaded into
  `tools/cache/`, verified and installed silently into `MILIONAR_INNO_PREFIX` (default
  `target/package/wine-inno`; the real home and `~/.wine` are refused after resolving
  links). Every wine process runs with `HOME=<prefix>-home` and without `XDG_*` overrides,
  winemenubuilder off and no Mono/Gecko, so the links wineboot makes (Desktop, Documents...),
  wine's caches and menu files stay out of the real home; the links are then replaced by
  plain folders inside the prefix. `wineserver -k` runs on exit.

Inno Setup 6.7 is free for non-commercial use only (its compiler prints "Non-commercial
use only"); any commercial use of this packaging needs a paid Inno Setup licence. The
compiled installer carries no Inno Setup licence obligation for the people who run it.

The installer: per-user install into `%LOCALAPPDATA%\Programs\Milionar` without
administrator rights by default (the first dialog offers an install for all users),
Start menu shortcut, optional desktop shortcut (unchecked), Czech and English, a licence
page (`license-cs.txt`, `license-en.txt`: GPL notice and the `vcomp140.dll` terms),
publisher `007hacky007`, fixed `AppId` `{0AD878F5-B731-4993-A000-AC7705DFED06}` (never
change it: Windows finds earlier installs by it), Windows 10+ x64 only, no Authenticode
signature. The uninstaller removes the install folder and shortcuts, then asks whether to
keep the imported game data and the upscaled pack in `%APPDATA%\milionar-port\Milionar`
(the data dir of `gamedata::default_data_dir()`, `dirs::data_dir()` = roaming AppData); a
silent uninstall keeps it. It never deletes after an all-users install (the uninstaller then
runs elevated, and `{userappdata}` may be the elevating administrator's, not the player's;
other users' data is never touched either way), nor when `milionar-port` or `Milionar` is a
junction or symbolic link (it would empty the target); both cases are logged and the
folder is kept.
